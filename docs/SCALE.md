# 规模机制：百万行工程怎么跑得动

> 1M–5M LOC 的项目里，失效的不是「流程不够全」，而是**上下文、影响面、吞吐、成本**。
> 本文件是 [DEVELOPMENT-PLAN.md](../DEVELOPMENT-PLAN.md) §9 的展开：每个规模约束对应一个可实现的机制。

---

## 1. 规模问题的六个约束

| 约束 | 在百万行项目里的表现 | 对本项目的含义 |
|---|---|---|
| **上下文** | 没人（包括 agent）能读全库 | 只能读「变更 + 影响集 + 相关契约」 |
| **影响面** | 改一个接口可能波及几十个调用方 | 影响分析必须机器化；未知即升 L2 |
| **吞吐** | 50–500 PR/周，评审是瓶颈 | 协议开销必须分层；L2 必须稀少 |
| **一致性** | 多团队各自为政，规则漂移 | 策略即代码、可继承、可审计 |
| **可追溯** | 审计要回答「这个版本凭什么发」 | 回执 + 外部证据引用，可离线复核 |
| **经济性** | 6× token 不可持续 | 分级预算、采样、缓存、便宜席位 |

## 2. 机制作用域上移（最关键的一张表）

小项目里按「变更/文件」判；百万行项目里，很多判据必须上移到**子系统/接口/项目**层。

| 机制 | 小项目作用域 | 百万行作用域 | 频率 |
|---|---|---|---|
| 对象辨识（Q1） | 单个变更是否可分解 | **子系统/项目**是否可分解；OCG 判定 | 季度/立项 |
| 假设台账（Q2） | 每个设计假设 | 变更级 + 架构决策级；L2 抽样验证 | 每次 L2 |
| 综合集成（Q3） | 每个评审 | **跨子系统/接口决策**才做多席位 | 每月/重大变更 |
| 七步评审（Q4） | 每个变更 | L2 用七步；L1 三步；L0 采样 | 每次变更 |
| 再评估（Q5） | 每个决策 | 接口基线/ADR/程序基线按季度 | 季度/事件 |
| 人签（Q6） | 每个定稿 | 接口 owner/架构师；L2 定稿 | L2 |
| 基线（Q8） | 每次提交 | **接口基线 + 发布基线** | 版本/接口变更 |
| 控制论（Q9） | 无 | 交付系统本身（WIP/时延/逃逸） | 周/月 |

**结论**：不要用文件级判据去管百万行项目；先判子系统/接口，再判变更。

## 3. 影响分析（Impact Analysis）

### 3.1 v1：注册表 + CODEOWNERS + git（确定性，无模型）

**输入**

- 变更文件集：`git diff --name-status <base>..<head>`。
- 子系统注册表：`.firetree/subsystems/*.json`（`id`、`paths[]` glob、`owners[]`、`interfaces[]`、`tests[]`）。
- 接口注册表：`.firetree/interfaces/*.json`（`id`、`kind`、`file`、`sha256`、`contract_test`、`consumers[]`）。
- CODEOWNERS：评审人与 owner。

**算法**

1. 每个变更文件 → 匹配子系统 glob；未匹配 → `unknown`。
2. 每个变更文件 → 匹配接口定义文件（或接口声明的 glob）；命中即接口变更。
3. 接口变更 → 取 `consumers[]` + 反向依赖（注册表里的 `depends_on`）。
4. 每个路径 → CODEOWNERS → 评审人。
5. `tests[]` → 建议必跑的测试集。
6. 置信度：全部映射且接口有 consumers → `high`；任一 `unknown` → `low`，**强制升 L2**。

**输出**

```json
{
  "tier": "L2",
  "reason": ["interface changed: billing.api", "unknown path: tools/legacy/x.py"],
  "impact": {
    "files": ["..."],
    "subsystems": ["billing", "checkout"],
    "interfaces": ["billing.api"],
    "owners": ["@team-billing", "@team-checkout"],
    "tests": ["billing/contract", "checkout/integration"]
  },
  "confidence": "high"
}
```

**原则**：宁可多包含，不可漏。漏报接口比多报成本高一个量级。

### 3.2 v2：接代码智能

- SCIP/索引：符号级引用，补充 `consumers`。
- LSP：实时定义/引用（用于评审时上下文，不用于批量）。
- 代码搜索（OCR 式确定性选文件）：补 `unknown` 路径的归属。

**不自己做**：不建索引、不做调用图；只消费。

### 3.3 评估

- 标注集：50 个真实变更，人工标注「受影响接口/子系统」。
- 指标：**召回率优先**（目标 ≥95%），精确率可放宽（≥70%）。
- 漏报事故 → 进入风险登记册；连续两次漏报 → 该路径强制 L2 并补注册表。

## 4. 评审吞吐

| Tier | 评审深度 | 轮数上限 | 时间盒 | 采样 |
|---|---|---|---|---|
| L0 | 1 轮轻评审 | 1 | 当天 | 10% 人工抽检 |
| L1 | 三步（准则/评审/结论） | 2 | 1 天 | 全量 |
| L2 | 七步 + 综合集成 | 3 | 3 天 | 全量 |

**吞吐机制**

1. **WIP 限制**：每个评审人同时 ≤3 个 L2；超限排队（不是降级）。
2. **异步评审**：作者不被阻塞；评审人批量处理。
3. **L2 配额**：L2 ≤15% 变更；超配额时平台团队必须解释或调整策略。
4. **采样**：只对 L0；采样决定写入回执。
5. **升级而非降级**：队列拥堵时不能把 L2 降成 L1；只能加人/调整策略。

**时延 SLO**：L0 当天、L1 ≤1 天、L2 ≤3 天；超时进入周报。

## 5. 成本模型

| Tier | token 预算 | 主要成本 | 控制手段 |
|---|---|---|---|
| L0 | ≤20k | 轻评审 | 单模型、diff 分片 |
| L1 | ≤100k | 三步评审 + 假设 | 单模型、按单元取 diff |
| L2 | ≤400k | 多席位 + 七步 + 双轮 | 席位模型分级、时间盒、缓存 |

**手段**

1. **懒加载**：技能正文按需；常驻 ≤2k tokens。
2. **按单元取 diff**：只取本变更/本单元；不贴全库。
3. **缓存**：影响集、接口哈希、评审包；同一 base/head 不重复计算。
4. **模型分级**：数据席位用便宜模型；经验席位与综合器用强模型。
5. **批量**：同子系统小变更可共享影响集；不共享评审结论。
6. **预算熔断**：单变更超预算 → 停止扩轮，输出部分结论并标记「未收敛」。

**度量**：每次变更记录 token（宿主可提供则读，否则用调用次数 × 估算）、时长、模型数。

## 6. 集成点与失败模式

| 集成 | 消费 | 产出 | 失败时 |
|---|---|---|---|
| git | diff、commit、tag | 变更工件 | 非 git → 明确报错 |
| CI | JUnit/JSON/SARIF/coverage/SBOM、run URL、OIDC | 回执校验、事件 | 证据缺失/过期 → 拒绝 |
| 接口注册表 | 接口定义、consumers、契约测试 | 影响集 | 注册表过期 → `low` 置信度 → L2 |
| CODEOWNERS | 评审人/owner | 评审席位 | 无法解析 → 人工指派 |
| 身份 | CI OIDC、SCM 用户 | signoff | 无身份 → A1 降级 |
| 制品库（可选） | 回执/证据引用 | 外置引用 | 不可达 → 本地引用 + A1 |

**失败原则**：宁可拒绝（fail-closed），不可静默降级。

## 7. 多团队与多仓

- **策略继承**：组织 → 仓库 → 子系统；子层可加严不可放松；放松需架构师批准 + 到期日。
- **多仓（v2）**：接口注册表跨仓；影响分析跨仓；回执引用跨仓证据。v1 单仓。
- **发布列车/供应商/可靠性增长**：明确不做；只输出「发布前回执是否齐全」。
- **团队自治**：L0/L1 策略可由团队自定（在组织下限内）；L2 统一。

## 8. 度量与 SPC

**图表（周级）**

- 逃逸缺陷率（按子系统/团队）
- 评审时延（P50/P90）
- L2 占比、例外率
- 误拦率
- token/PR、评审轮数
- 回执完整率

**基线**：pilot 前 4 周；控制限用移动极差；越界即查特殊原因。

**控制动作**：调采样率、调 WIP、调 L2 配额、补注册表、改策略；不调指标定义。

**禁止**：用 LOC、发现数、评审轮数当 KPI（古德哈特）。

## 9. 推广路径

| 阶段 | 范围 | 时长 | 退出条件 |
|---|---|---|---|
| P1 | 1 个子系统、1 团队 | 4 周 | 误拦<5%、回执可用、团队愿意继续 |
| P2 | 产品线 3–5 子系统 | 8 周 | 策略模板、跨子系统影响分析、L2 路径跑通 |
| P3 | 组织（多团队/多仓） | 12 周 | 采纳≥80%、例外<5%、指标看板 |

**采纳战术**：黄金路径（模板/一条命令）、冠军团队、可见收益（时延/逃逸）、逃生通道（热修例外）。

## 10. 反模式

| 反模式 | 后果 | 替代 |
|---|---|---|
| 所有变更走 L2 | 吞吐崩溃、团队绕过 | 分级 + 采样 |
| 用 LLM 猜影响面 | 漏报、不可复现 | 注册表 + 确定性算法 |
| agent 自证/自签 | 审计失效 | 外部证据 + 人签 |
| 全量人工评审 | 时延爆炸 | L0 采样、L1 轻评审 |
| 用 LOC/发现数考核 | 指标失真 | 逃逸率/精确率/时延 |
| 多团队同一策略 | 冲突、绕过 | 继承 + 例外 + 到期 |
| 回执当装饰 | 无人校验 | CI gate + 抽样审计 |
